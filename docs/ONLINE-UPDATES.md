# 正式发布在线升级

从 1.3.0 起，检查更新、安装和程序恢复均进入统一后台任务。刷新或关闭网页不会取消任务；重新打开“管理维护 → 任务与恢复”可查看结果。不会定时自动安装。

## 首次切换

旧版升级器无法被新版本的发布说明改变。首次切换到 1.3.0，建议下载正式 Release 的 Windows ZIP，右键“全部解压”，将里面的 IPK 上传到路由器安装。安装完成后刷新面板并核对当前版本。从 1.3.0 开始的后续在线升级才使用本文的新流程。

## 升级流程

1. 检查固定仓库的最新正式 Release，排除草稿和预发布；解析轻量或附注标签实际指向的提交。main 上尚未发布的提交不会成为升级目标。
2. 校验版本递增、提交快进关系及同一提交 push CI 的成功状态。检查本地依赖、可用空间、未保存 UCI 修改及配置锁。
3. 固定 Release、标签、提交、附件 ID、大小和 GitHub 提供的 SHA-256。确认升级后后台重新核对；附件变化时要求重新检查更新。
4. 将 `phone-panel-update.tar.gz` 下载到临时目录，核对实际大小和 SHA-256，再限制文件数量、展开大小、路径和文件类型后解包。损坏或中断的下载不会开始替换程序。
5. 校验 `update-manifest.json` 的格式、最低升级器要求、版本、提交、所有文件内容及权限。清单必须完整、不重复且无未声明文件，禁止覆盖设备和网络数据。新增代码文件由清单声明，不依赖旧版硬编码映射。
6. 获取配置锁，重新核对当前程序版本和空间。检查暂存程序语法、依赖，备份当前配置及所有即将替换的程序文件，持久保存恢复记录。
7. 逐个原子替换并同步程序文件，逐项复核安装后的内容和权限，再写入部署提交标记。更新监测服务和 LuCI 缓存，验收状态接口、设备数、原先正常的监听和保护，并核对网络进程与受保护配置没有变化。
8. 全部通过才记录安装成功。设备持久化迁移仍需单独预览、确认，不会随程序更新自动执行。

## 失败和中断

- 下载、清单或语法检查失败：停止，保留当前程序。
- 安装或服务验收失败：尝试恢复操作前程序，再分别核对文件和服务。只有两项通过才标记恢复成功。
- 进程被终止或路由器重启：根据启动标识、进程身份和持久记录识别未完成安装；不自动重试升级或迁移，阻止继续安装。
- “文件恢复通过”不能代替“运行态恢复通过”。状态不确认时，到“版本与更新 → 恢复之前的程序版本”选择带有“未完成升级”标记的记录。后台恢复只还原程序，保留当前设备数据；持久化格式不兼容的旧快照会被拒绝。
- 如果面板本身无法打开，使用 LuCI 软件包页安装同一正式版本的完整 IPK 修复程序文件，或通过 SSH 检查 `/root/phone-panel-releases` 的记录。不要删除恢复快照或根据版本号猜测安装成功；必要时先保存路由器备份。

在线升级由面板管理程序文件；opkg 的基础安装包版本可能与面板显示的程序版本不同。完整 IPK 安装由 opkg 管理，版本和文件清单来自同一发布构建。

## 发布与测试

正式标签必须与 VERSION 一致，先通过完整 Linux CI，再从同一提交构建安装包和文件清单。所有附件上传到草稿后才公开；工作流拒绝覆盖已公开的 Release。`RELEASE_SHA256SUMS.txt` 校验 Release 的实际附件，Windows ZIP 内的 `SHA256SUMS.txt` 校验解压后的文件。

回归包括七个旧版布局夹具、缺少新增服务、损坏下载、附件变化、清单缺失/损坏/权限/格式错误、磁盘写满、失败恢复验收和 Linux 中安装进程被真实 SIGKILL。夹具不等同于运行七台旧路由器；实机断电、文件系统故障、固件差异及手机真实业务仍需部署验收。不能承诺所有硬件和外部服务条件下都不会失败。
